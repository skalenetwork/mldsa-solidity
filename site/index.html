mldsa-solidity verifies ML-DSA (FIPS 204, formerly CRYSTALS-Dilithium) signatures entirely inside the EVM, in pure Solidity. ML-DSA is the lattice signature NIST chose as the primary replacement for ECDSA, and the one hardware wallets and HSMs are starting to sign with. This library lets a contract check those signatures today, with no precompile and no new chain. 

import {IMLDSAVerifier, ML_DSA_44} from "mldsa-solidity/IMLDSAVerifier.sol";
// true iff sig is a valid ML-DSA-44 signature on message under publicKey
bool ok = verifier.verify(ML_DSA_44, publicKey, message, sig);
// the same verifier, through the scheme-neutral IPQVerifier (ML-DSA-44 = 0x0101)
bool same = IPQVerifier(verifier).verify(PQAlgorithms.ML_DSA_44, publicKey, message, sig);

Why this exists

A large enough quantum computer breaks ECDSA, and with it every Ethereum account, multisig and bridge key. NIST's answer, standardised in 2024, is ML-DSA: a lattice signature with small keys, fast signing, and no state to track, so a key can sign as often as it likes and can be restored from a backup.

Ethereum has no ML-DSA precompile. A draft proposal for one exists (EIP-8051), but it is not scheduled. Until it ships, the only way for a contract to accept an ML-DSA signature is to verify it in Solidity. That is what this library does, within one transaction's gas budget.

Swappable by design

Contracts depend on an interface, never on this implementation: IMLDSAVerifier, or IPQVerifier, which SLH-DSA and FN-DSA verifiers answer too. When an ML-DSA precompile or an audited verifier ships, an adapter takes its place behind the same call, with no redesign.

Precomputed keys

Everything a verification needs that depends only on the public key is computed once, on-chain, and stored as contract code. That cuts ML-DSA-65 verification from 9.15M gas to 3.68M, and ML-DSA-87 from 14.09M to 5.39M.

Trust by address

Precomputed data lives at a CREATE2 address derived from the key's hash, and only the factory can write there. A caller stores 32 bytes and trusts the data because of where it is.

Setting up a key

  1. registerT(set, pk): compute tr and NTT(t₁·2d) from the key and store them.
  2. registerA(set, pk): compute the matrix Â and store it. Or split it: commitA computes it and records only its hash, and storeA stores the bytes later, accepted only if they match. That keeps a wallet's whole setup inside one transaction. ML-DSA-87's Â is over the 24,576-byte code limit, so it is kept in two parts, each with its own commitment: registerAPart and storeAPart handle one part per transaction.
  3. Verify. MLDSAVerifier takes the fast path when the key's data is registered, and verifies from scratch when it isn't. Both paths give the same answer.

Key ids that outlive keys

MLDSAKeyRegistry gives an ML-DSA key a stable id, keccak256(registrant, salt), that stays the same while the key behind it changes. The registrant picks the first key and keeps no power over the id afterwards. From then on only the current key can hand the id on, by signing an EIP-712 RotateKey message over the id, the version it replaces, the new parameter set and the new key's hash. Each rotation signature works exactly once.

ML-DSA keeps no per-signature state, so rotation is never forced: it is for suspected compromise, routine renewal, or moving up a parameter set, from ML-DSA-44 to ML-DSA-87 and back.

The calls

register(salt, set, pk)Create the id with its first key
rotate(id, set, pk, sig)Replace the key; sig is by the current key, anyone may submit it
verify(id, msg, sig)Check a signature by the key currently behind the id
getKey(id)Set, public key and version

Gas

Measured with forge test at 32-byte messages. Everything fits under the EIP-7825 per-transaction cap of 224 (16.78M) gas, except a single-call registerA for ML-DSA-87, which is why it comes in parts.

Through IPQVerifier the same verification costs 144 to 184 gas more. A key-registry rotation from one ML-DSA-87 key to another, the most expensive kind, is 15.13M gas as a transaction when the current key is not precomputed and 6.42M when it is.

Sign a 32-byte digest, such as an EIP-712 hash. Each extra 136 bytes of message adds about 89k gas; for ML-DSA-87 without precomputation, a 3,000-byte message comes within about 0.5M of the cap.

Why you should believe it

NIST's own vectors

The official ACVP ML-DSA-sigVer-FIPS204 vectors for all three sets, external and internal interfaces, including every case NIST expects to fail. Pinned at usnistgov/ACVP-Server@a7f283c.

An independent implementation

Differential vectors from dilithium-py, compared byte for byte, intermediate values and precomputed data included. One script regenerates every fixture.

Stricter than the reference

dilithium-py accepts a repeated hint index, which FIPS 204 Algorithm 21 forbids. This library rejects it, as the standard requires, and a test pins the difference.

Plus negative tests for bit flips, wrong lengths, every hint-encoding rule, the exact ‖z‖∞ boundary and keys used under the wrong parameter set, and fuzzing. Every vector also runs through IPQVerifier, on the precomputed path and the fallback, and must give the same answer; unknown algorithm ids are false, never a revert.

Unaudited. This is new cryptographic code. It passes NIST's vectors and agrees with an independent implementation, but no third party has reviewed it. Weigh that before securing value with it.

Quickstart

# add the library to a Foundry project
forge install skalenetwork/mldsa-solidity
# remappings.txt
mldsa-solidity/=lib/mldsa-solidity/src/
pq-verifier-interface/=lib/mldsa-solidity/lib/pq-verifier-interface/src/
@openzeppelin/contracts/=lib/mldsa-solidity/lib/openzeppelin-contracts/contracts/
import {IMLDSAVerifier, ParamSet, ML_DSA_44} from "mldsa-solidity/IMLDSAVerifier.sol";

contract Vault {
    IMLDSAVerifier public immutable verifier;   // fixed at deployment

    constructor(IMLDSAVerifier v) { verifier = v; }

    function check(bytes calldata pk, bytes32 digest, bytes calldata sig) external view returns (bool) {
        return verifier.verify(ML_DSA_44, pk, abi.encodePacked(digest), sig);
    }
}

Deploy MLDSAKeyFactory and MLDSAVerifier once, register each key with the factory for the fast path, and run forge test to see every vector pass.
